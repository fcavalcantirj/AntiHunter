# ESP32-S3 N16R8 target

`AntiHunter-n16r8-full` targets an ESP32-S3-WROOM-1 N16R8 module: 16 MB QIO flash and 8 MB octal PSRAM. It runs the existing full firmware and uses the SoftAP web interface as its control surface. The legacy external SD, GPS, DS3231 RTC, vibration input, GPS PPS, and Meshtastic UART are disabled at compile time, so the generic target does not claim those GPIOs.

## Safety boundary

The commands below compile and emulate only. They do not enumerate USB devices, upload firmware, erase flash, change a partition table on hardware, or write eFuses. Do not add `-t upload` until the module marking, flash/PSRAM geometry, USB recovery procedure, and desired peripheral pin map have been checked on the exact physical board.

## Compile the hardware image

```bash
pio run -e AntiHunter-n16r8-full
```

PlatformIO's `esp32-s3-devkitc1-n16r8` manifest supplies `default_16MB.csv`, QIO flash, octal PSRAM, and `BOARD_HAS_PSRAM`.

## Wokwi

The root `wokwi.toml` and `diagram.json` model an ESP32-S3 with 16 MB flash and 8 MB octal PSRAM. `wokwi.toml` uses PlatformIO's merged `firmware.factory.bin`, which includes the matching bootloader, partition table, and application. After building the hardware image:

```bash
wokwi-cli . --timeout 60000 --expect-text "ANTIHUNTER DIGINODE v1.0.2 STABLE BOOT COMPLETE"
```

Wokwi CLI requires `WOKWI_CLI_TOKEN`. Its CLI and several supporting projects are open source, but the ESP32 simulation runs on Wokwi's hosted service. Running this command therefore sends the firmware artifacts and diagram to a third party; obtain explicit approval before doing so. Wokwi emulates ESP32-S3 boot, memory, GPIO, UART, I2C, SPI, and basic Wi-Fi, but not Bluetooth. This is therefore a boot/memory test, not an RF acceptance test.

The validated run initialized 8 MB octal PSRAM, allocated all three detection queues in PSRAM, started the SoftAP and web server, observed the boot-complete marker, and returned `TEST PASSED`.

## Physical board: offline SoftAP check

Joining the board's isolated `Antihunter` access point disconnects the Mac from the internet. Any remote Codex session will therefore drop while the Mac is associated with the board; this is expected and is not a firmware failure.

Start the read-only CLI validator in a local Terminal before changing Wi-Fi:

```bash
cd /path/to/AntiHunter
./scripts/antihunter validate --wait 180
```

Then join `Antihunter` (default password `antihunt3r123`) from the macOS Wi-Fi menu. The dependency-free Python 3 CLI waits up to three minutes for `http://192.168.4.1`, checks the web UI and diagnostics, validates the JSON API, and confirms that the running device reports usable PSRAM. It performs HTTP `GET` requests only and does not flash, erase, reboot, or change settings. `scripts/verify_n16r8_board.sh` remains as a compatibility wrapper around the same validator.

The raw responses and summary are saved under `hardware-test-results/`. When the script finishes, reconnect the Mac to its normal internet-connected Wi-Fi and review the newest report.

## Espressif QEMU

Espressif QEMU requires a DIO flash image and exposes UART0 rather than the board's USB-CDC console, so build the separate emulator-only target:

```bash
pio run -e AntiHunter-n16r8-qemu
```

Merge or pad the generated bootloader, partition table, boot app, and application into a 16 MB raw flash image, then run it with Espressif's QEMU fork using machine `esp32s3`. The `AntiHunter-n16r8-qemu` output is not a physical-device artifact.

The repository includes a runner that validates the QEMU binary, creates a temporary 16 MB flash image, and removes it on exit:

```bash
AH_QEMU_BIN=/path/to/espressif/qemu-system-xtensa scripts/run_qemu_n16r8.sh
```

The expected smoke-test marker is `ANTIHUNTER DIGINODE v1.0.2 STABLE BOOT COMPLETE`. After it appears, press `Ctrl-A`, then `X`, to exit QEMU's multiplexed serial console.

QEMU does not model the ESP32-S3 RF path, octal PSRAM, or the attached real-world peripherals. The QEMU target therefore disables Wi-Fi/BLE initialization and is expected to report that PSRAM is absent while continuing through its fallback path. A successful boot proves that the CPU can execute the image and that early flash/application initialization is coherent under the emulator; it does not prove PSRAM operation, Wi-Fi promiscuous capture, BLE scanning, antenna performance, or final pin safety. Use the Wokwi model for virtual 8 MB octal-PSRAM and basic Wi-Fi coverage.
